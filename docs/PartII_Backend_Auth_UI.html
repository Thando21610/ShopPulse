1.Scope & Governing Decisions

These twelve decisions govern every flow described in this document. Each is chosen for reliability over novelty, because 55% of the Samsung mark is about fit and judgement, not technical spectacle.

#DecisionRationale
D1Access token is a short-lived JWT held in memory onlyNever in localStorage. Removes the largest XSS token-theft surface.
D2Refresh token is an opaque random string in an HttpOnly cookieJavaScript cannot read it, so XSS cannot exfiltrate it.
D3Frontend and API are served same-origin via a Cloudflare Pages Function proxyMakes the refresh cookie first-party. Avoids third-party cookie blocking in Chrome, Safari and Firefox.
D4Refresh tokens rotate on every useEach refresh issues a new token and revokes the old one.
D5Refresh token reuse revokes the whole familyDetects token theft and forces a clean re-login.
D6Only SHA-256 hashes of refresh tokens are storedA database leak does not yield usable sessions.
D7One refresh may be in flight at a time (single-flight)Prevents rotation races that would trip reuse detection on the user's own tab.
D8Every error is a ProblemDetails body with a stable codeLets the UI branch on machine-readable codes instead of parsing English.
D9Server validation is the source of truth; client validation is a courtesyInstant feedback without ever trusting the client.
D10Validation errors render inline, centered, red — never as a toastToasts vanish; field errors must persist next to the offending input.
D11All writes that create money or stock movement carry an idempotency keyNetwork retries cannot double-charge or double-deduct.
D12Success is shown only after the server commitsPessimistic UI for anything financial. No optimistic toasts.

Every authenticated call follows the same thirteen stages. Understanding this pipeline once means understanding every screen in the application.

        |

        |

        |

    Failure  -> ProblemDetails with { code, errors, correlationId }
        |

      403      -> pass through (no refresh; the user is authenticated but not allowed)
        |

      success  -> toast (or silent) + update state
      failure  -> inline field errors and/or banner and/or toast, per §16
Why 401 triggers a refresh but 403 does not A 401 means "I don't know who you are" — the token may simply have expired, so refreshing is worth one attempt. A 403 means "I know exactly who you are, and you may not do this" — refreshing would produce an identical 403. Retrying it would only double the load and confuse the user.

3.Same-Origin Proxy Decision

This is the single most consequential wiring decision in the document, so it is justified explicitly.

3.1 The problem

Cloudflare Pages (shoppulse.pages.dev) and Cloud Run (shoppulse-api-xxxx.run.app) are different sites. A cookie set by the API is therefore a third-party cookie when read from the frontend origin. Safari's ITP and Chrome's ongoing third-party cookie restrictions make that unreliable for a graded demonstration.

3.2 Options compared

OptionHow it worksVerdict
Recommended A — Pages Function proxy A Cloudflare Pages Function at /api/* forwards to Cloud Run. The browser only ever talks to shoppulse.pages.dev. First-party cookie. No CORS. No third-party cookie risk. Costs one small JS file.
Fallback B — Direct cross-origin + IndexedDB Blazor calls Cloud Run directly; refresh token stored in IndexedDB, sent in a request body. Works today, but the refresh token becomes JS-readable, defeating D2. Use only if the proxy is blocked.
Rejected C — SameSite=None cookie API sets a cross-site cookie with SameSite=None; Secure. Depends on third-party cookie support that browsers are actively removing. Not a safe foundation.
Rejected D — Access token in localStorage Long-lived JWT in browser storage. Trivially exfiltrated by any XSS. Disqualified on security grounds.

3.3 Proxy implementation

A single file at /functions/api/[[path]].js in the Pages project:

// functions/api/[[path]].js  — Cloudflare Pages Function
export async function onRequest(context) {
  const { request, env, params } = context;
  const target = env.API_ORIGIN;              // e.g. https://shoppulse-api-xxxx.run.app
  const path   = (params.path || []).join("/");
  const url    = new URL(request.url);

  const upstream = new URL(`${target}/api/${path}`);
  upstream.search = url.search;

  const headers = new Headers(request.headers);
  headers.set("X-Forwarded-Host", url.host);
  headers.delete("host");

  const init = {
    method: request.method,
    headers,
    redirect: "manual",
    body: ["GET", "HEAD"].includes(request.method) ? undefined : request.body,
  };

  const res = await fetch(upstream.toString(), init);

  // Pass Set-Cookie through untouched so the browser binds it to this origin.
  const out = new Headers(res.headers);
  out.delete("content-encoding");   // fetch has already decoded the body
  out.delete("content-length");

  return new Response(res.body, {
    status: res.status,
    headers: out,
  });
}
Cookie attributes still matter Because the proxy makes everything first-party, the API should set the refresh cookie with Domain omitted (host-only), Path=/api/auth, SameSite=Strict, Secure and HttpOnly. The cookie is then only transmitted on the two endpoints that need it, which is exactly the intent.

3.4 What the proxy does not solve

  • It does not replace authentication — the API still validates every JWT.
  • It does not weaken authorisation — role checks remain server-side.
  • It does not remove the need for HTTPS — Cloudflare and Cloud Run both enforce it.

4.Token Model & TTLs

Why 15 minutes and not 60 A longer access token means a stolen token stays valid for longer. Fifteen minutes with silent refresh is invisible to the user and materially reduces the blast radius. The 60-second skew window absorbs normal clock drift between Cloud Run instances and the browser.

4.2 Why the idle and absolute limits differ

  • Idle limit (7 days) — a user who does not open the app for a week must sign in again. This closes abandoned sessions on shared devices.
  • Absolute limit (30 days) — even a continuously active session cannot live forever. Rotation cannot extend it past the original family's start date.

5.Refresh Rotation & Reuse Detection

Rotation is the mechanism that turns a static secret into a self-defending one. Each refresh consumes the presented token and issues a replacement. A token is therefore single-use.

5.1 The mechanism

  1. Client presents refresh token R1.
  2. Server validates R1: exists, not revoked, not expired.
  3. Server issues R2 in the same family and marks R1 as revoked with ReplacedByTokenId = R2.
  4. Server returns a new access token and the new R2 cookie.
  5. If R1 is ever presented again, the server knows it was already used — a signal that it was captured.

5.2 Family model

Login ──► R1 ──rotate──► R2 ──rotate──► R3 ──rotate──► R4
          │              │              │              │
          └──────────────┴──────────────┴──────────────┘
                    all share FamilyId = F

Reuse of R1 detected
        │
        ▼
Revoke every token in family F
        │
        ▼
All future refreshes with any R in F return 401 AUTH_REFRESH_REUSED
        │
        ▼
User is redirected to /login

5.5 Rotation service

public sealed class RefreshTokenService
{
    private readonly AppDbContext _db;
    private readonly RefreshTokenOptions _opt;

    public (string Raw, RefreshToken Entity) Rotate(RefreshToken current)
    {
        var now = DateTimeOffset.UtcNow;
        var raw = GenerateRaw();                    // 32 random bytes, base64url

        var next = new RefreshToken
        {
            Id           = Guid.NewGuid(),
            UserId       = current.UserId,
            FamilyId     = current.FamilyId,
            TokenHash    = Hash(raw),
            CreatedAtUtc = now,
            // Idle window restarts, but never beyond the family's absolute cap.
            ExpiresAtUtc = Min(now.AddDays(_opt.IdleDays), current.FamilyAbsoluteExpiry),
        };

        current.RevokedAtUtc      = now;
        current.RevokedReason     = "ROTATED";
        current.ReplacedByTokenId = next.Id;

        return (raw, next);
    }

    public async Task RevokeFamilyAsync(Guid familyId, string reason, CancellationToken ct)
    {
        await _db.RefreshTokens
            .Where(t => t.FamilyId == familyId && t.RevokedAtUtc == null)
            .ExecuteUpdateAsync(s => s
                .SetProperty(t => t.RevokedAtUtc, DateTimeOffset.UtcNow)
                .SetProperty(t => t.RevokedReason, reason), ct);
    }

    private static string GenerateRaw()
        => Base64UrlEncode(RandomNumberGenerator.GetBytes(32));

    public static string Hash(string raw)
        => Convert.ToBase64String(SHA256.HashData(Encoding.UTF8.GetBytes(raw)));
}
The one legitimate source of reuse A race where two browser tabs refresh simultaneously could present the same token twice and falsely trigger family revocation. The single-flight handler in §9 exists specifically to prevent this on the client. On the server, an optional 5-second grace window on a just-rotated token is a reasonable mitigation — but it weakens the detector, so it should be a deliberate, documented trade-off, not a default.

7.1 What is deliberately absent

  • Permissions are not enumerated in the token; the role maps to a server-side policy table so permissions can change without waiting for token expiry.

9.Single-Flight Refresh Handler

This handler is the heart of the frontend wiring. It attaches the token, refreshes proactively when the clock says so, and coordinates a single refresh across every in-flight request.

9.2 The handler

public sealed class AuthMessageHandler : DelegatingHandler
{
    private static readonly SemaphoreSlim Gate = new(1, 1);

    private readonly ITokenStore _tokens;
    private readonly IHttpClientFactory _factory;
    private readonly NavigationManager _nav;
    private readonly IToastService _toasts;
    private readonly ILogger<AuthMessageHandler> _log;

    private static readonly TimeSpan RefreshWindow = TimeSpan.FromSeconds(60);

    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct)
    {
        // ---- 1. Proactive refresh if the token is about to expire -------------
        if (_tokens.IsExpiringWithin(RefreshWindow))
            await RefreshOnceAsync(ct);

        // ---- 2. Attach the bearer token ---------------------------------------
        AttachToken(request);

        // ---- 3. Buffer the body so the request can be replayed ----------------
        //      Only buffered when the content is repeatable-safe.
        var buffered = await BufferIfNeededAsync(request, ct);

        // ---- 4. First attempt --------------------------------------------------
        var response = await base.SendAsync(request, ct);

        if (response.StatusCode != HttpStatusCode.Unauthorized)
            return response;

        // ---- 5. Reactive refresh + one retry ----------------------------------
        _log.LogInformation("401 received; attempting refresh before retry.");

        var refreshed = await RefreshOnceAsync(ct);
        if (!refreshed)
        {
            _tokens.Clear();
            _toasts.Warning("Your session ended. Please sign in again.");
            _nav.NavigateTo("/login?reason=session-expired");
            return response;
        }

        using var retry = await CloneAsync(request, buffered, ct);
        AttachToken(retry);

        return await base.SendAsync(retry, ct);
    }

    // -------------------------------------------------------------------------

    private void AttachToken(HttpRequestMessage request)
    {
        var token = _tokens.Current;
        if (token is null) return;
        request.Headers.Authorization = new AuthenticationHeaderValue("Bearer", token.Value);
    }

    private async Task<bool> RefreshOnceAsync(CancellationToken ct)
    {
        await Gate.WaitAsync(ct);
        try
        {
            // Another request may have refreshed while we waited.
            if (!_tokens.IsExpiringWithin(RefreshWindow))
                return true;

            var client = _factory.CreateClient("auth");   // handler-free client
            using var res = await client.PostAsync("api/auth/refresh", content: null, ct);

            if (!res.IsSuccessStatusCode)
                return false;

            var body = await res.Content.ReadFromJsonAsync<RefreshResponse>(cancellationToken: ct);
            if (body is null) return false;

            _tokens.Set(new AccessTokenSnapshot(body.AccessToken, body.ExpiresAtUtc));
            return true;
        }
        catch (Exception ex) when (ex is HttpRequestException or TaskCanceledException)
        {
            _log.LogWarning(ex, "Refresh call failed.");
            return false;
        }
        finally
        {
            Gate.Release();
        }
    }

    private static async Task<byte[]?> BufferIfNeededAsync(
        HttpRequestMessage request, CancellationToken ct)
    {
        if (request.Content is null) return null;
        return await request.Content.ReadAsByteArrayAsync(ct);
    }

    private static async Task<HttpRequestMessage> CloneAsync(
        HttpRequestMessage original, byte[]? body, CancellationToken ct)
    {
        var clone = new HttpRequestMessage(original.Method, original.RequestUri);

        foreach (var header in original.Headers)
            clone.Headers.TryAddWithoutValidation(header.Key, header.Value);

        if (body is not null)
        {
            clone.Content = new ByteArrayContent(body);
            foreach (var header in original.Content!.Headers)
                clone.Content.Headers.TryAddWithoutValidation(header.Key, header.Value);
        }

        await Task.CompletedTask;
        return clone;
    }
}
Why the body must be buffered An HttpRequestMessage cannot be sent twice — its content stream is already consumed. Retrying a POST therefore requires re-creating the request with a fresh content object. The buffered byte array makes that possible and keeps idempotency keys intact across the retry.
Never refresh on 403 The handler only reacts to 401. A 403 is a definitive authorisation decision and refreshing would produce the same result — burning a rotation for nothing and risking a false reuse detection.

10.Proactive vs Reactive Refresh

StrategyWhen it runsCostBenefit
Proactive Before sending, if exp - now < 60 s One extra round trip, off the critical path of the user's action The user never sees a 401, never sees a retry delay, and the request succeeds first time
Reactive After receiving a 401 The user's request pays for a wasted round trip Handles server-side revocation, clock drift, and tab-wake-from-sleep that proactive checks cannot predict

Both are used. Proactive refresh handles the ordinary case cheaply; reactive refresh is the safety net. A request that arrives in a fresh tab after a laptop sleeps will have an obviously expired token, which the proactive check catches immediately. A token revoked by an administrator will only surface as a 401, which the reactive path handles.

10.1 Startup flow

Because the access token lives only in memory, a page reload starts with no token. The app performs one silent refresh on boot:

App.razor OnInitializedAsync
   |
   +-- POST /api/auth/refresh   (cookie sent automatically)
   |
   +-- 200 -> TokenStore.Set(...)
   |          GET /api/auth/me

Why a page refresh is not a logout The user experience is "I refreshed the page and I am still signed in." The security posture is "the access token never touched persistent storage." The refresh cookie bridges the two. This is the whole reason the token pair exists.

    public ApiClient(HttpClient http) => _http = http;

    public Task<Result<T>> GetAsync<T>(string url, CancellationToken ct = default)
        => SendAsync<T>(new HttpRequestMessage(HttpMethod.Get, url), ct);

    public Task<Result<T>> PostAsync<T>(string url, object body, string? idempotencyKey = null,
        CancellationToken ct = default)
    {
        var req = new HttpRequestMessage(HttpMethod.Post, url)
        {
            Content = JsonContent.Create(body),
        };
        req.Headers.Add("Idempotency-Key", idempotencyKey ?? Guid.NewGuid().ToString("N"));
        return SendAsync<T>(req, ct);
    }

    public Task<Result<Unit>> DeleteAsync(string url, CancellationToken ct = default)
        => SendAsync<Unit>(new HttpRequestMessage(HttpMethod.Delete, url), ct);

    // ---------------------------------------------------------------------

    private async Task<Result<T>> SendAsync<T>(HttpRequestMessage req, CancellationToken ct)
    {
        try
        {
            using var res = await _http.SendAsync(req, ct);

            if (res.IsSuccessStatusCode)
            {
                if (res.StatusCode == HttpStatusCode.NoContent || typeof(T) == typeof(Unit))
                    return Result<T>.Ok(default!);

                var data = await res.Content.ReadFromJsonAsync<T>(cancellationToken: ct);
                return Result<T>.Ok(data!);
            }

            return Result<T>.Fail(await ReadProblemAsync(res, ct));
        }
        catch (TaskCanceledException) when (!ct.IsCancellationRequested)
        {
            return Result<T>.Fail(ApiError.Network());   // timeout
        }
        catch (HttpRequestException)
        {
            return Result<T>.Fail(ApiError.Network());
        }
    }

    private static async Task<ApiError> ReadProblemAsync(
        HttpResponseMessage res, CancellationToken ct)
    {
        try
        {
            var problem = await res.Content.ReadFromJsonAsync<ProblemDetailsPayload>(cancellationToken: ct);
            if (problem is not null)
                return new ApiError(
                    problem.Code ?? "UNKNOWN",
                    problem.Detail ?? problem.Title ?? "Something went wrong.",
                    (int)res.StatusCode,
                    problem.Errors,
                    problem.CorrelationId);
        }
        catch (JsonException) { /* fall through */ }

        return new ApiError(
            "UNKNOWN",
            "Something went wrong. Please try again.",
            (int)res.StatusCode,
            null,
            null);
    }
}

public static class ValidationMapper
{
    public static void ApplyTo(
        EditContext editContext,
        IReadOnlyDictionary<string, string[]> fieldErrors)
    {
        var messageStore = new ValidationMessageStore(editContext);

        foreach (var (fieldName, messages) in fieldErrors)
        {
            var identifier = editContext
                .FieldIdentifiers()
                .FirstOrDefault(f =>
                    string.Equals(f.FieldName, fieldName, StringComparison.OrdinalIgnoreCase));

            if (identifier == default)
            {
                // Unmapped error -> surface as a form-level banner
                messageStore.Add(new FieldIdentifier(editContext.Model, string.Empty),
                    messages.First());
                continue;
            }

            foreach (var message in messages)
                messageStore.Add(identifier, message);
        }

        editContext.NotifyValidationStateChanged();
    }
}

17.Toast System Specification

17.1 Behaviour

  • Rendered in a fixed host at the top-right on desktop, bottom-center on mobile.
  • Maximum of 4 visible; the oldest is evicted when a fifth arrives.
  • Identical messages within a 2-second window are deduplicated.
  • Success and info auto-dismiss; errors auto-dismiss but remain manually closable.
  • Hovering pauses the dismiss timer.
  • Announced via aria-live="polite"; errors use role="alert".
  • Never stacks on top of a modal's own feedback.

17.2 Service

public enum ToastKind { Success, Info, Warning, Error }

public sealed record Toast(Guid Id, ToastKind Kind, string Message, string? Detail, int DurationMs);

public interface IToastService
{
    event Action? Changed;
    IReadOnlyList<Toast> Visible { get; }

    void Success(string message, string? detail = null);
    void Info(string message, string? detail = null);
    void Warning(string message, string? detail = null);
    void Error(string message, string? detail = null);
    void Dismiss(Guid id);
}

public sealed class ToastService : IToastService
{
    private readonly List<Toast> _items = new();
    private readonly Dictionary<string, DateTimeOffset> _recent = new();

    public event Action? Changed;
    public IReadOnlyList<Toast> Visible => _items;

    public void Success(string message, string? detail = null)
        => Push(ToastKind.Success, message, detail, 4_000);

    public void Info(string message, string? detail = null)
        => Push(ToastKind.Info, message, detail, 4_000);

    public void Warning(string message, string? detail = null)
        => Push(ToastKind.Warning, message, detail, 6_000);

    public void Error(string message, string? detail = null)
        => Push(ToastKind.Error, message, detail, 8_000);

    private void Push(ToastKind kind, string message, string? detail, int durationMs)
    {
        var key = $"{kind}|{message}";
        var now = DateTimeOffset.UtcNow;

        if (_recent.TryGetValue(key, out var last) && now - last < TimeSpan.FromSeconds(2))
            return;                                   // deduplicate

        _recent[key] = now;

        if (_items.Count >= 4)
            _items.RemoveAt(0);

        _items.Add(new Toast(Guid.NewGuid(), kind, message, detail, durationMs));
        Changed?.Invoke();
    }

    public void Dismiss(Guid id)
    {
        _items.RemoveAll(t => t.Id == id);
        Changed?.Invoke();
    }
}

The scenario that matters: two operators sell the last loaf of bread at the same moment.

21.1 Mechanism

Every row that holds mutable quantity carries a concurrency token. EF Core includes it in the WHERE clause of the UPDATE. If zero rows are affected, the write is rejected.

21.3 UI behaviour on conflict

  3. A Refresh button reloads the cart lines from the server.
  4. The operator adjusts and resubmits with a new idempotency key, because the intent has changed.

22.2 Sale safety under uncertainty

If a sale request times out, the operator must not be told it failed without qualification. The correct sequence is:

  1. Show: "We could not confirm whether your sale was recorded."
  2. Offer Check status, which re-sends with the same idempotency key.
  3. The server replays the original response if the sale did commit, or processes it fresh if it did not.
  4. Only then does the UI show the definitive outcome.

This is the reason idempotency exists. Without it, the only safe message is "unknown," which is useless in a shop.

Why two named clients If AuthMessageHandler used the same client it decorates, a failed refresh would trigger another refresh, which would trigger another — an infinite loop. The "auth" client bypasses the handler entirely. This is a small detail with large consequences.

27.Security Checklist

  • Access token held in memory only — no localStorage, no sessionStorage, no IndexedDB
  • Refresh token HttpOnly, Secure, SameSite=Strict, Path=/api/auth
  • Refresh tokens stored as SHA-256 hashes only
  • Rotation on every refresh; reuse revokes the family
  • Absolute session cap enforced independently of the idle window
  • JWT signature, issuer, audience and lifetime validated on every request
  • ClockSkew set to 60 s — not the 5-minute default
  • Tenant ID read from the token claim only — never from the request
  • Every tenant-owned entity carries a global query filter
  • Role checks on every endpoint; 403 returned before any business logic
  • Rate limiting on /api/auth/login and /api/auth/refresh
  • Account lockout after repeated failures
  • Password hashed with ASP.NET Core Identity defaults (PBKDF2)
  • Secrets in Cloud Run environment / secret manager — never in Git
  • Connection string never reaches the Blazor WASM bundle
  • HTTPS enforced end to end; HSTS enabled
  • No passwords, tokens or full request bodies in logs
  • Idempotency keys stored per business, hashed request body compared
  • Audit events written in the same transaction as the business change
  • No real personal data anywhere in the demo dataset

30.Acceptance Criteria

Part II is considered implemented when all of the following are demonstrably true in the deployed application.

Authentication

  • Logging in returns an access token and sets an HttpOnly refresh cookie visible in DevTools with the correct flags
  • The access token does not appear in localStorage, sessionStorage or any cookie
  • Refreshing the page keeps the user signed in via the silent refresh on boot
  • Refresh rotates: a second refresh call in DevTools shows a different cookie value
  • Replaying an old refresh token returns AUTH_REFRESH_REUSED and forces re-login
  • Logout clears the cookie and the old token no longer refreshes

Request pipeline

  • An expired access token produces exactly one refresh call, then a successful retry — visible in the Network tab
  • Three simultaneous 401s produce exactly one /api/auth/refresh request
  • A 403 never triggers a refresh
  • A cross-tenant request returns 404, not 200

Validation & feedback

  • Submitting an invalid form shows centered red text under each offending field with a ⚠ prefix
  • Invalid inputs carry aria-invalid="true" and a red border
  • Validation errors are never delivered as toasts
  • Successful writes show a success toast; failed writes show either inline errors or a banner — never both for the same message
  • Every toast is readable on a 360 px wide screen

Data integrity

  • Submitting the same sale twice with the same idempotency key creates one sale
  • Two concurrent attempts on the last unit produce one success and one CONCURRENCY_CONFLICT
  • No completed sale is ever deleted; corrections are refunds
  • Every write that moves stock or money produces an audit event in the same transaction

Resilience

  • A simulated cold start shows the info banner and the request still completes
  • Going offline mid-form disables submit and shows the offline banner
  • A timed-out sale retry produces exactly one sale
  • A 500 shows the correlation ID so the failure can be traced in logs
What Part II deliberately does not cover Password reset emails, MFA and social login are out of scope for the pilot — each adds surface area without addressing the validated problem. They are documented as "next with more time" in the walkthrough rather than half-built.
